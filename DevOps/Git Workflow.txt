I finally had a look at how you're supposed to use GitHub, and it's really quite easy I thought it was more complicated

We will have 2 standard branches - Main and Development

Main will be the stable, demo branch that is always runnable and stable, where we will tag releases and eventually run our live demo

Development will be obviously where we will code - and periodically we will merge this with the main to update the working demo (probably at sprint meetings)

this is the main part - how we will add code (This is up to date as of 19/01/2026, and I will try to find all other conflicting instructions and update those)

when you want to make a feature (e.g a new API endpoint) - (make sure your local repo is up to date) you branch Development, creating a new branch e.g API view for satistics graph 1

then, commit all your code to this branch as you are coding, you should be the only one using this branch so there should be no conflicts

when you are finished writing the feature, and all the unit tests you have written pass, you submit a pull request

The appropriate technical lead will then accept or deny the pull request depending on the quality of code and testing and give feedback if the pull request was denied

these pulls will then add features to the Development Code base in a structured, easy to view manner

The development code base can be merged to the main codebase when stable to produce a a snapshot of the current stable runnable release
We should do this at each sprint meeting, then run and test both servers from a client perspective to try and find any improvements we could make
